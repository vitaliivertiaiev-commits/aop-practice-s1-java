# Практична 5: Git — `.gitignore` та припинення відстеження

Запуск усієї демонстрації:

```bash
bash scripts/practice-5.sh git
```

Або запусти DevOps і Git послідовно однією командою:

```bash
bash scripts/practice-5.sh all
```

Вправа працює тільки у новій теці `~/dev/git5.*` і не виконує push. Навчальний
файл `.env` містить лише явно фальшиве значення `NOT_A_REAL_CREDENTIAL`.
Не копіюйте до нього справжні паролі, токени або ключі.
У цьому середовищі Git глобально ігнорує `.env`, тому тимчасовий репозиторій
використовує локальний `core.excludesFile=/dev/null`, щоб показати крок із
відстеженням `.env` до додавання правила проєкту.

Після кожного з п'яти блоків сценарій чекає Enter, щоб можна було зберегти скриншот.

## 1. Ігнорування збірки та локальних налаштувань

Поки немає `.gitignore`, `target/Main.class`, `.idea/workspace.xml` і `Main.java`
відображаються в `git status`. Після додавання правил `target/` і `.idea/`
залишаються тільки потрібні вихідний файл та `.gitignore`.

## 2. Відстежуваний `.env`

`.gitignore` не припиняє відстеження файла, який уже потрапив до Git. Команда
`git rm --cached .env` прибирає його з індексу, але залишає на диску.
Приклад токена в сценарії фальшивий і залишається тільки в тимчасовому репозиторії.
Якщо справжній секрет опубліковано, видалення наступним комітом його не захищає:
секрет потрібно відкликати та замінити.

## 3. Шаблони та винятки

Правила `logs/`, `*.log`, `!keep.log` і `/build` показують ігнорування каталогів,
файлів за розширенням, виняток через `!` та прив'язку шаблону до кореня.
`src/deep.log` ігнорується, `keep.log` та `src/build/example.txt` залишаються
видимими в `git status`.

## 4. Перевірка правил і безпечне прибирання

`git check-ignore -v` показує файл правил, рядок і шаблон, який ігнорує шлях.
Перед `git clean -fd` сценарій виконує `git clean -n`, щоб показати, що буде
видалено. Обидві команди працюють лише у тимчасовому демонстраційному репозиторії.

## 5. Файл між гілками

Сценарій створює `draft` до появи `Main.java` на `main`, окремо комітить файл на
`main`, прибирає його з відстеження через `git rm --cached`, а тоді додає й комітить
на `draft`. Перевірка `git ls-tree` показує різний вміст гілок. Потім файл
відновлюється окремим комітом на `main`.

У методичці наведено коротший набір команд, але якщо `draft` створити вже після
того, як `Main.java` закомічений на `main`, обидві гілки успадкують цей коміт.
Саме `git rm --cached` змінює індекс і не переписує історію гілки; щоб перенести
файл між гілками, сценарій фіксує вилучення на `main` і додавання на `draft`
окремими комітами.
