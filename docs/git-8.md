# Практична 8. Git: скасування змін

Вправи виконуються в тимчасовому локальному репозиторії.

## 1–2. Amend

```bash
git commit --amend -m "правильне повідомлення"
git add b.txt
git commit --amend --no-edit
git show --stat HEAD
```

`--amend` замінює останній коміт, тому його хеш змінюється.
`--no-edit` зберігає повідомлення, але включає підготовлений файл `b.txt`.
У виправленому коміті є обидва файли: `a.txt` і `b.txt`.

## 3. Два restore

Після однієї підготовленої й однієї непідготовленої правки
`git status -s` показує `MM a.txt`.

```bash
git restore --staged a.txt
git status -s
cat a.txt
git restore a.txt
cat a.txt
```

Перша команда прибирає файл зі staging, але залишає обидві правки.
Друга повертає вміст з індексу. У цій послідовності індекс уже відповідає
коміту, тому незакомічені правки зникають.

## 4. Три reset

Після трьох комітів із рядками `рядок 1`, `рядок 2`, `рядок 3`:

| Команда | HEAD | Індекс і робочі файли |
| --- | --- | --- |
| `git reset --soft HEAD~1` | Попередній коміт | Правка залишається staged |
| `git reset --mixed HEAD~1` | Попередній коміт | Правка залишається unstaged |
| `git reset --hard HEAD~1` | Попередній коміт | Індекс і файл повертаються до нього |

Перед кожним варіантом відновлюється третій коміт, щоб початковий
стан був однаковим. Після `--hard` у `log.txt` залишаються два рядки.

## 5. Reflog

```bash
git reflog
```

У журналі можна знайти хеш третього коміту й повернути його командою
`git reset --hard <хеш>`. Третій рядок з'являється знову, бо він був
закомічений і об'єкт ще зберігається в локальному репозиторії.
Це не спосіб повернення довільних незакомічених правок.

## 6. Revert

```bash
git revert HEAD --no-edit
git log --oneline
cat log.txt
```

`revert` створює новий коміт зі зворотною зміною. Третій рядок зникає,
але початковий коміт залишається в історії.
Для спільної вже опублікованої історії це безпечніше за `reset`.
