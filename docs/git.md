# Git: навіщо існує контроль версій

## Чим контроль версій кращий за копії файлів

Набір на кшталт `report.docx`, `report_v2.docx`, `report_final.docx` і
`report_final_FIXED_2.docx` — це ручна система версій. Вона погано відповідає на чотири
питання:

1. **Що змінилося?** Доводиться відкривати файли й порівнювати їх вручну.
2. **Чому змінилося?** Причина лишилася лише в пам'яті автора.
3. **Хто змінив?** Якщо людей кілька, це важко встановити.
4. **Як поєднати роботу?** Дві паралельні копії можуть перезаписати одна одну.

Резервна копія переважно відповідає на «дай учорашній файл». Контроль версій зберігає
історію станів проєкту, дає змогу порівнювати їх і бачити авторів та повідомлення про зміни.
Git записує коміти — іменовані знімки файлів; гілки та злиття допомагають працювати з
паралельними змінами. GitHub — сервіс для віддаленого зберігання й спільного перегляду
Git-репозиторіїв.

## Перевірити Git і налаштувати автора

```bash
git --version
git config --global user.name "Ім'я Прізвище"
git config --global user.email "you@example.com"
git config --list
git config --list --show-origin | grep user
```

Замініть ім'я та адресу на власні. `--list --show-origin` показує не лише параметри, а й файл,
з якого вони взялися — зазвичай це `~/.gitconfig`. Відкрийте цей текстовий файл, щоб побачити,
де збережені глобальні налаштування. Ім'я та пошта записуються в коміт і стають його
постійною частиною.

## Переконатися, що identity входить у коміт

Виконуйте тест лише в тимчасовій теці, не в репозиторії практичної:

```bash
mkdir -p /tmp/identity-test && cd /tmp/identity-test
git init
echo "first" > a.txt
git add a.txt
git commit -m "first commit"
git log --format='%h %an <%ae> %s'
```

Тепер перевизначте пошту тільки для цього репозиторію та створіть другий коміт:

```bash
git config user.email "someone-else@example.com"
echo "second" >> a.txt
git commit -am "second commit"
git log --format='%h %an <%ae> %s'
```

У результаті перший і другий коміти мають різні адреси автора. Глобальне значення є типовим,
а локальне налаштування репозиторію його перекриває. Зміна налаштування не переписує старі
коміти: коміт — уже створений об'єкт історії.

## Прочитати історію репозиторію

```bash
git clone https://github.com/vitaliivertiaiev-commits/aop-practice-s1-java.git
cd aop-practice-s1-java
git log --oneline -5
git log --oneline -20
```

У цій практичній історія покаже коміти, створені під час підготовки репозиторію. Порівняйте
повідомлення: хороше пояснює майбутньому читачеві, що було зроблено; порожнє або загальне
повідомлення мало допомагає зрозуміти причину змін.

## Відповіді на запитання з практичної

- `git log` показує історію, авторів і повідомлення комітів — це допомагає з'ясувати, **хто**
  та **чому** вносив зміни.
- `git diff` показує, **що саме** відрізняється між файлами або станами.
- **Поєднання паралельної роботи** потребує злиття змін і розглядається пізніше у треку
  (заняття 9–11, зокрема заняття 10).

## Типовий цикл роботи

```bash
git status
git add src docs readme.md
git status
git commit -m "Complete practice 1"
git push
```

`git add` готує вибрані файли, `git commit` зберігає знімок локально, `git push` передає
коміти у віддалений репозиторій. Після push перевірте на GitHub, що файли та останній коміт
з'явилися.
